Study 05 · Super Downloader

The engine is somebody else's problem

A local interface over yt-dlp, built in an afternoon for two people. The interesting part was not the interface. It was discovering that the one platform I had written off as easy was the one that did not work at all — and why.

Runs on 127.0.0.1 Engine yt-dlp 2026.08.19 Dependencies Python stdlib Build step none
01 — The premise

Write the part that does not exist yet

yt-dlp carries 1,752 extractors, maintained by hundreds of people reacting continuously to platforms that change specifically to break them. Rewriting any of that would be the only genuinely unmaintainable decision available.

So this does not. It is a queue, a progress bar, a folder structure and an interface, wrapped around an engine somebody else keeps alive. When Instagram changes something, the fix is brew upgrade yt-dlp, not a weekend.

That is the whole architectural idea, and it is worth stating plainly because it inverts the usual instinct. The hard part was already solved and given away. What was missing was the twenty minutes of ergonomics on top — a place to paste a link, somewhere sensible for files to land, and a way to see what is happening.

The whole tool

Platforms that need a login read cookies from a browser already signed in, via yt-dlp's --cookies-from-browser. No password is ever typed into this thing, and none is stored. That is both simpler to build and the safer design, which is a pleasant coincidence rather than a trade.

02 — Where it broke

The easy platform was the broken one

Ranking the five by expected difficulty before building: YouTube and Pinterest easy, X moderate, Instagram and Facebook hard. That ranking was right about four of them.

The first real Pinterest link came back with this:

[Pinterest] 7951736838825829: Download Pin JSON metadata
ERROR: [Pinterest] 7951736838825829: No video formats found!

Two things in those two lines. The extractor succeeded at reading the pin — so this was not a block, a cookie problem or a rate limit. And then it found no video.

yt-dlp is a video tool. Pinterest is mostly images. On an image pin it does not degrade gracefully — it reports no formats and writes nothing at all, not even the thumbnail you explicitly asked for. Which makes the platform I had called "easy" the one platform the tool could not handle.

The fix is not a yt-dlp problem to report upstream. It is correctly refusing to do a job it is not for. The fix belongs in the thing wrapped around it.

03 — What Pinterest returns

One header is the difference between 403 and 200

To save the image, you need the pin's metadata. Requesting it the obvious way fails:

curl -A "Mozilla/5.0 … Chrome/120 Safari/537.36" \
  "https://www.pinterest.com/resource/PinResource/get/?data=…"

http 403  50 bytes  (and gzipped, so it does not even print)

A convincing user agent is not enough. Pinterest answers 403 to anything that does not look like its own front end. What gets a 200 is a header the React app sends and nothing else does — the same one yt-dlp uses, which is why the extractor got its metadata while a hand-rolled request did not:

X-Pinterest-PWS-Handler: www/[username]/[slug].js

With that header the same request returns the pin in full. And the pin turns out to have three possible shapes, only one of which anything to do with video:

What a pin can be

Plain imageimagesOne rendition set, orig included
Carouselcarousel_dataSeveral slots, each with its own rendition set — and no orig
Idea Pinstory_pin_dataPages of blocks, each block an image or a video
Video pinvideosThe only one yt-dlp handles, and it handles it well

The pin that started this was a carousel of three images. yt-dlp was entirely right; the message just was not useful. Reading the metadata directly and saving each slot turns a dead end into three files.

04 — The trap

"originals" is not the original

Pinterest's CDN serves the same asset under several path segments — 236x, 474x, 736x, originals. Carousel slots list renditions only up to 736x and carry no orig key, so the obvious move is to rewrite the path and take the original instead.

That assumption is wrong, and quietly so. Measuring all three slots of the pin:

736x against originals, same three images
Slot736xoriginalsDimensions
151,658 B47,163 B720 × 900 both
262,679 B57,030 B720 × 900 both
3112,042 B101,297 B720 × 900 both

Identical pixel dimensions, consistently fewer bytes. For this pin the upload was 720 × 900 to begin with, and originals is a differently-compressed copy rather than a larger one. Taking it would have silently thrown away image quality while feeling like an upgrade — the worst kind of bug, because nothing fails and the output looks fine.

So the code does not assume. It asks:

# i.pinimg.com serves the same asset under several path segments. The
# 'originals' copy is sometimes bigger and sometimes just re-compressed at
# identical dimensions, so pick by bytes rather than by faith.
alt = re.sub(r"i\.pinimg\.com/[^/]+/", "i.pinimg.com/originals/", url, count=1)
a, b = _content_length(alt), _content_length(url)
return alt if a > b else url

Two HEAD requests, and the question is settled per image instead of per assumption.

05 — The other bug

Editing a file and watching nothing happen

Halfway through building the Pinterest fallback, it did not fire. The logic was right — called directly it saved the files — but through the running server the old error came back unchanged.

The server had never restarted. An older instance still held port 7788, so the new one exited immediately on Address already in use and the stale process kept answering. The kill pattern matched an absolute path; the process was running under a relative one.

The failure mode is the problem, not the collision. A port conflict is ordinary. What made it cost twenty minutes is that the symptom — code changes having no effect — points at the code, which was fine, rather than at the process, which was stale.

So the tool now says it in words rather than in a traceback:

  Port 7788 is already in use by pid 13925.
  That is probably an older Super Downloader still running, which
  means edits to server.py will appear to do nothing.

    ./run.sh                       restart cleanly (recommended)
    python3 server.py --replace    same thing, spelled out
    kill 13925                     just stop it

And the banner prints its own pid, so there is never a question about which instance is answering. Naming the likely cause in the error is a smaller change than it feels like, and it is the difference between a minute and an afternoon.

06 — What it will not do

The lines that are deliberate

No extractors of its own. Every platform-specific behaviour except the Pinterest image path lives in yt-dlp. The Pinterest exception exists only because it falls outside what a video tool is for.

DRM is a hard stop. yt-dlp refuses DRM-protected content and this does too. A DRM error is the end of the road, not a bug to route around.

It is not a web service, and it structurally cannot become one. This is worth showing, because it is the same question anyone asks on seeing a browser interface. Serving the page from a static host:

The interface on a static host
RequestResult
GET /200 — the page loads perfectly
GET /api/jobs404
POST /api/add501

The page is a front end for a process on one machine. Its five endpoints spawn a subprocess, which no static host can do. Uploading the interface somewhere public would produce something that looks exactly like the tool and does nothing — a convincing shell, which is worse than shipping nothing at all.

That constraint is doing useful work. A local tool is a tool; the same thing hosted is a service, with somebody else's bandwidth, somebody else's abuse to police, and a very different relationship to the content passing through it. The version that runs on your own machine is the version worth having.

07 — What it cost

An afternoon, and one wrong assumption

The interface took an afternoon. The Pinterest path took longer than the interface, for a platform originally filed under easy — and most of that time went on two things that looked like facts and were not: that a convincing user agent is enough, and that a path segment called originals contains originals.

Both were cheap to check and expensive to assume. The header cost one request to discover. The compression cost three HEAD requests. Neither would have announced itself: the first fails loudly and misleadingly, the second does not fail at all.

The tool itself is unremarkable, which is the point — it is three files and no dependencies, and it works because the difficult 95% of it is somebody else's ongoing labour, freely given. Most of what I learned building it was about Pinterest's front end, which I had not set out to learn anything about.

Study 05. Built for two people and run on their own machines; the tool is not published, because a downloader that runs on someone else's server is a different object with different consequences.

The engine is yt-dlp, which does all the difficult parts and asks for nothing.
